# Moonwell Core — Design

- **Date:** 2026-09-24
- **Status:** Approved design, pending spec review
- **Scope:** Sub-projects 1 (core toolchain) and 2 (data layers) of the Moonwell roadmap

## 1. Summary

Moonwell is a Warcraft III map development framework in which gameplay is written in
[YueScript](https://github.com/IppClub/YueScript) and project data (configuration, object
data, asset imports, map settings) is written in [Pkl](https://pkl-lang.org). The toolchain
is a Deno CLI published to JSR. Pkl schemas are published as a versioned Pkl package. A map
project contains only its own content.

Moonwell's feature set is modelled on `wc3-dev-framework` (TypeScript + TSTL + Pkl + Deno),
but Moonwell is an independent codebase: it copies and adapts ideas and code where useful and
shares nothing at runtime.

### Hard constraints

- **No Node.js.** No `package.json`, no `node_modules`, no `npm:` specifiers, and no npm
  packages in map projects or in the Moonwell repo. The repo root sets `nodeModulesDir: "none"`. Only
  `jsr:` imports (`@std/*`).
- Gameplay code is YueScript compiled to Lua 5.3, which is the Lua version Warcraft III runs.
- Pkl is required for anything that reads project configuration.

### Roadmap (each sub-project gets its own spec → plan → implementation cycle)

1. **Core toolchain** *(this spec)*: project model, Yue compile, bundler, runtime hooks,
   staging, MPQ packaging, launch, watch.
2. **Data layers** *(this spec)*: Pkl object data, asset imports, map settings.
3. **Editor & DX** *(later)*: LuaLS/Yue declarations for natives and World Editor globals,
   lint rules for gameplay code, compile-time macros (e.g. rawcode → integer at compile time).
4. **Libraries & runtime** *(later)*: library sync (the `libraries` config key), typed
   wrappers over natives (w3ts equivalent), YueScript port of `wc3-lib`.

## 2. Verified facts this design relies on

Checked on 2026-09-24:

- YueScript v0.34.2 publishes `yue-windows-x64.7z` (SHA-256
  `367e79f450dc60d96d248c8e1d97b4ec47729b963f64226888fb8e111fc349bf`),
  `yue-windows-x86.7z` and `yue-linux-x86_64.zip`. macOS has no standalone CLI asset.
- Windows' built-in `%SystemRoot%\System32\tar.exe` (bsdtar) extracts the `.7z`.
- `yue --target=5.3 -r -t <out> <srcdir>` compiles a directory tree, mirrors paths
  (`src/a/b.yue` → `out/a/b.lua`), keeps source line numbers, and emits
  `import "a.b" as B` as `require("a.b")`.
- `yue -e <code|file>` executes Lua on an embedded Lua 5.4 VM. Moonwell uses this for runtime tests.
- `package://pkg.pkl-lang.org/github.com/<owner>/<repo>/<name>@<ver>` redirects to
  `https://github.com/<owner>/<repo>/releases/download/<name>@<ver>/<name>@<ver>`.
  A GitHub release tagged `moonwell@<ver>` can therefore host the Pkl package.
- The development machine has Pkl 0.32.1 and Deno 2.x.

## 3. Repositories and layout

### 3.1 Moonwell repo (this repository)

```

    src/main.ts             argument parsing and command dispatch

    src/project/            Pkl evaluation of the manifest, typed Project, version check

    src/bundle/             Lua lexer, require graph, module emission, injection, line table
    src/mpq/                MPQ v1 writer (crypto tables, hashing, sectors, listfile)
    src/w3i/                war3map.w3i read/patch for supported versions

    src/assets/             asset planning, war3map.imp, check/sync, ownership state

    data/metadata.json      vendored object metadata (generated by gen:metadata, committed)
    tests/                  unit + integration + e2e tests, fixtures
  schema/                   Pkl package "moonwell"

    Project.pkl             root manifest schema

    objects/                Unit/Hero/Building/Item/Ability/Buff/Upgrade classes

  tools/                    repo-only Deno scripts: gen, gen-metadata, gen-schema, release

```

JSR modules cannot reliably read their own non-TypeScript files when run from a remote
specifier. So `deno task gen` converts `cli/runtime/*.lua`, `cli/data/metadata.json` and every
file under `template/` into TS modules in `cli/src/embedded/`. Binary files become base64.
Generated modules are committed, and a test fails if they are stale.

### 3.2 Map project (what `init` creates)

```
my-map/
  deno.json                tasks → jsr:@moonwell/cli@<ver> (no package.json, so Deno creates no node_modules)
  PklProject               dependency on package moonwell@<ver>
  PklProject.deps.json     resolved + checksummed (committed)
  moonwell.pkl             project manifest (amends "@moonwell/Project.pkl"), everyday settings written out
  moonwell.local.pkl       git-ignored; amends "moonwell.pkl"; machine-specific values; made by init/setup
  src/main.yue             gameplay entry
  src/generated/objects.yue  generated object ids (committed)
  objects/*.pkl            object definitions (any file layout; see §6.1)
  assets/                  files to import
  maps/map.w3x/            World Editor source map (folder format, Lua script mode)
  .asset-state/            asset ownership state (committed)
  dist/                    build output (git-ignored)
  .gitignore
```

If the JSR scope `@moonwell` is unavailable, the CLI is published as
`@mdlsvensson/moonwell-cli`. Nothing else in this design changes.

### 3.3 Project manifest

`@moonwell/Project.pkl` defines:

```pkl
map { folder: String = "map.w3x"; entry: String = "src/main.yue" }
build { folder: String = "dist/bin"; minify: Boolean = false }   // not "output": every Pkl module already has a built-in `output`
launch { gameExecutable: String?; args: List<String> = List("-launch", "-windowmode", "windowed") }  // a List, so assigning replaces the default
yue { version: String = "0.34.2"; path: String? }   // path: use a local compiler build
settings: MapSettings = new {}
assets: AssetsConfig = new {}
objects: Objects = new {}
```

`map.folder` and `build.folder` must be relative paths without `..` (no leading `/` or `\`, no drive letter).
`build.folder` also cannot be, or be under, `maps`, `src` or `dist/stage`, because a build deletes the previous
archive. As a second guard, `build` refuses an output path outside the project or one that is a directory.

Every field is optional with defaults.

**Settings files.** Settings are enabled, not commented out:

- **Everyday settings are written out.** The `moonwell.pkl` written by `init` sets them to their defaults, so a user
  edits values instead of uncommenting lines. It contains the `amends` line, `map`, `build`, `launch.args`, the objects
  wiring line (§6.1) and the enabled `settings` and `assets` blocks.
- **Advanced settings are left out but documented.** `yue` (compiler version and path) is not in the file. It is
  documented in the schema's doc comments and the README, and it keeps its default unless someone sets it. New settings
  follow the same split.
- **Only settings that need a World Editor step first stay commented out**, each with a note naming that step (§6.3).
- **`moonwell.local.pkl`.** `init` writes it, and `setup` recreates it when missing, because it is git-ignored and a
  fresh clone has none. Neither ever overwrites it. It amends `moonwell.pkl` and sets `launch.gameExecutable` to the
  default Windows install path.
- **Lists are `List`, not `Listing`.** Amending a `Listing` default in Pkl (`args { ... }`, and even `args = new
  { ... }`) appends to it, so a written-out list would duplicate the default. Assigning a `List` replaces it.

The schemas live only in the package, never in the project.

**Loading.** The CLI evaluates `moonwell.local.pkl` if it exists, otherwise `moonwell.pkl`,
using `pkl eval --format json --project-dir <root>`. It then parses the output into a
TypeScript `Project` type that mirrors the schema.

**Version check.** The CLI reads the resolved `moonwell` package version from
`PklProject.deps.json`. If its major.minor differs from the CLI's own version, the CLI fails
with an upgrade hint.

## 4. Commands

Map-project tasks (all `deno run -A jsr:@moonwell/cli@<ver> <command>`):

| Command | Behaviour |
| --- | --- |
| `init <dir>` | Scaffold §3.2 into an empty or new directory, then run `pkl project resolve`. |
| `setup` | Install the pinned `yue` into the user cache. Run implicitly by build/test/dev/check. |
| `build [--entry f] [--minify]` | Full pipeline (§5) → `<build.folder>/<map folder name>` (a packed `.w3x`, default `dist/bin`). |
| `test [--entry f]` | Pipeline without packing; launch the game on the staged folder map. |
| `dev` | Watch `src/`, `objects/`, `assets/`, `moonwell*.pkl`. Recompile changed Yue files, re-evaluate Pkl, regenerate `objects.yue`, print errors. No hot reload. |
| `check` | Compile all Yue, resolve the require graph, evaluate and validate the manifest, objects, settings and assets (read-only). No game and no packing. |
| `objects:eval` | Print the evaluated, validated object manifest as JSON. |
| `assets:check` / `assets:sync` | Same semantics as wc3-dev-framework (§6.2). |
| `settings:check` | Evaluate and validate settings; show the planned changes without writing them. |

Repo tasks: `test`, `test:runtime`, `test:pkl`, `test:e2e`, `lint`, `fmt`, `gen`,
`gen:metadata`, `gen:schema`, `release`.

## 5. Build pipeline

Order, shared by `build`, `test` and (partially) `check`:

1. **Lock.** Create `dist/.lock` exclusively. A second concurrent build fails fast. The lock
   is removed in `finally`.
2. **Load project** (§3.3).
3. **Ensure compiler** (§5.1).
4. **Compile Yue** (§5.2).
5. **Evaluate data.** Objects, settings and assets from the manifest. Only the `assets` configuration is read
   here: the files under `assets/` are collected and applied in step 7, against the staged copy.
6. **Stage.** Copy `maps/<folder>` into `dist/stage/<folder>` (e.g. `dist/stage/map.w3x`), replacing any previous
   staging. The staged folder keeps the `.w3x` name because the game loads folder maps by that name.
7. **Apply.** Object data (§6.1), then settings (§6.3), then assets (§6.2) to the staged map.
8. **Bundle and inject** (§5.3, §5.4) into the staged `war3map.lua`.
9. **Pack** (§7) for `build`, or **launch** for `test`.

If any step fails, `build` deletes `dist/bin/<map>` so an older archive is never mistaken for
a fresh one.

### 5.1 Compiler install

- **Cache directory:** `%LOCALAPPDATA%\moonwell\yue\<version>\` on Windows, and
  `$XDG_CACHE_HOME/moonwell/yue/<version>/` (default `~/.cache/...`) on Linux.
- **Known versions.** The CLI embeds a table of known versions: version → platform →
  (asset URL, SHA-256). An unknown `yue.version` without `yue.path` is an error that lists the
  known versions.
- **Install steps:**
  1. Download to a temporary file.
  2. Verify the SHA-256.
  3. Extract. On Windows this uses `System32\tar.exe`. On Linux it uses a built-in minimal
     zip reader based on `DecompressionStream("deflate-raw")`.
  4. Check that `yue -v` reports the expected version.
  5. Atomically rename into the cache.
- **`yue.path`** skips the download. The CLI still checks `yue -v` and warns on a version
  mismatch.
- **macOS** is unsupported unless `yue.path` is set.

### 5.2 Compile

- **Invocation:** one `yue --target=5.3 -r -o dist/stage/lua/<path>.lua src/<path>.yue` per changed
  file (up to 8 at a time), rather than a single `-t` call over the directory. Per-file calls
  make incremental builds possible and tie each compiler error to its file and line.
- **Incremental builds.** A content-hash manifest (`dist/stage/lua/.hashes.json`) lets repeat
  builds and `dev` compile only changed files. Deleted sources remove their outputs.
- **Errors.** Compiler errors are reported with the `.yue` file and line and fail the build.
- **`--minify`** adds `-m`. Line mapping is then disabled: the bundle sets `__mw.minified`, and errors
  name the module's `.yue` file without a line number.
- **Module name.** A module's name is its path relative to `src/`, without the extension,
  with `/` replaced by `.`. For example, `src/heroes/captain.yue` is `heroes.captain`.

### 5.3 Require graph and bundle

- **Lexer.** A Lua 5.3 lexer tokenizes each compiled module, skipping comments and
  short/long strings.
- **Recognized form:** `require` followed by a string literal, either `require("x")` or
  `require "x"`.
- **Build errors, each with file and line:**
  - a `require` whose argument is not a single string literal;
  - a module not found (the message lists the search roots);
  - a cycle (the message prints the chain).
- **Search roots.** `dist/stage/lua/`, plus the built-in runtime module `moonwell`. Library
  roots come in sub-project 4.
- **Reachability.** Starting from the entry module (`map.entry` or `--entry`), only reachable
  modules are emitted.
- **Bundle layout:**
  1. The runtime prelude (the embedded `moonwell.lua`).
  2. One `__mw.define("x.y", function(...) <module source> end)` per module.
  3. The line table.
  4. The boot: `__mw.boot("<entry>")`.

  The boot requires the entry at script load under `xpcall`. As with TSTL, module top-level
  code runs at load time, so gameplay should create game handles only inside hooks.
- **Line table.** A sorted array of `{bundleStartLine, moduleName, sourcePath}`, computed
  after injection so offsets are absolute within `war3map.lua`.

### 5.4 Runtime (`moonwell` module, Lua)

**API**
- `on_config(fn)`, `on_main(fn)`, `before_config(fn)`, `before_main(fn)`: register hooks.
  Multiple registrations run in registration order.
- `require(name)`, the shim: `package.loaded`-style cache. It never touches the filesystem.
- `format_error(msg, traceback)`: rewrites `war3map.lua:<n>:` and
  `[string "war3map.lua"]:<n>:` positions to `<sourcePath>:<line>:` using the line table.

**Hooks and error handling**
- **Wrapping.** At the end of the bundle, the runtime saves the World Editor's global
  `config` and `main` and replaces them with wrappers:
  - `config`: `before_config` hooks → original `config` → `on_config` hooks;
  - `main`: the same pattern with the main hooks.
- **Isolation.** Each hook and the boot run under `xpcall`. A failing hook prints its
  formatted error on screen with `print` and does not stop the others. The original
  `config`/`main` also run under `xpcall`.
- **Lua version.** The runtime uses only Lua 5.3-compatible features.

**Example**

```yue
import "moonwell" as mw
import "generated.objects" as objects

mw.on_main ->
  CreateUnit Player(0), objects.units.captain, 0, 0, 270
  CreateUnit Player(0), FourCC("hfoo"), 128, 0, 270
```

Base-game ids use the game's `FourCC` at runtime in this spec. A compile-time rawcode macro
arrives with sub-project 3.

### 5.5 Injection

The bundle is appended to the staged `war3map.lua`. The CLI checks that the file defines both
`function main` and `function config`. If either is missing, it fails and says the map must
be saved in Lua script mode. This does not use `war3-transformer` or any TypeScript tooling.

## 6. Data layers

### 6.1 Object data

**Metadata** (`cli/data/metadata.json`) is generated by the repo-only `gen:metadata` task.
It reads SLKs that the maintainer extracts once from the game into a local folder, which is
never committed:
- `UnitMetaData`, `AbilityMetaData`, `AbilityBuffMetaData`, `UpgradeMetaData`;
- the id lists from `UnitData`, `ItemData`, `AbilityData`, `AbilityBuffData`, `UpgradeData`.

Per field it records:
- rawcode, friendly name, value type, category;
- the applicable object types (e.g. ability code for ability-specific fields);
- whether the field is per-level, and its data column (A–I);
- whether it's a skin field.

Per category it records base-object ids and, for abilities and upgrades, the base level count.

**Pkl package** (`schema/`):
- `ObjectFile.pkl` declares the seven optional category mappings: `heroes`, `units`,
  `buildings`, `items`, `abilities`, `buffs`, `upgrades`. Keys must match
  `[A-Za-z_][A-Za-z0-9_]*`. Values are the typed classes in `pkl/objects/`, which extend the
  generated `*Props` classes.
- Each object has `id` (4 alphanumeric characters, typed per category as in wc3-dev-framework),
  `base` (a generated `Bases.pkl` union), typed properties, and a `properties` escape hatch
  keyed by friendly name or raw field rawcode.
- `Objects.pkl` provides `merge(files: Mapping<String, ObjectFile>): Objects`. It throws a Pkl
  error naming both files when two files define the same category key. Each merged object
  records its `source` file path.

**Project wiring** (written by `init`):

```pkl
import "@moonwell/Objects.pkl"
objects = Objects.merge(import*("objects/**.pkl"))
```

Users can organize `objects/` however they like: by category, or by feature (a hero, its
abilities and its buffs in one file).

**Values:**
- Scalars set the field (level 1 or the only value).
- A `List` sets levels 1..n on a per-level field.
- `null` means inherit from the base.
- Explicit `false`, `0`, `""` and empty lists are overrides.
- `stringList`-typed fields accept a `List<String>` joined with commas.

**Validation** runs over the whole manifest before anything is written. Errors are reported
as `<source> › <category>["<key>"].<field>: <problem>`. It rejects:
- a non-4-character or non-alphanumeric rawcode;
- a duplicate id across all categories;
- a missing base, with a nearest-rawcode suggestion;
- an id that collides with a base object or an existing custom object in the source map's
  tables;
- an unknown field, or a field not applicable to the base;
- a `List` on a field that is not per-level;
- more list entries than the object's level count, taken from its `levels` property or the
  base's.

**Modification files**
- **Coverage.** `cli/src/objectdata/` reads and writes:
  - simple tables `w3u`, `w3t`, `w3h`;
  - leveled tables `w3a`, `w3q`;
  - their `war3mapSkin.*` counterparts.

  `w3b`/`w3d` and any other files are copied untouched.
- **Merging.** Existing custom and modified objects in the source map are preserved. New
  objects are appended to the custom table. Each field goes to the standard or skin file
  according to its skin flag.
- **Versions.** Formats 1–3 are read. Each file is written at the version it was read at. A
  new file uses the version of the map's other modification files, or version 2 if the map
  has none. §11 confirms that the game reads version 2 on current builds.

**Generated ids.** `src/generated/objects.yue` exports one table per category, mapping key →
integer id (the rawcode packed big-endian, matching `FourCC`). It is rewritten only when its
content changes. `check` fails if it is stale.

### 6.2 Assets

Ported from wc3-dev-framework with the same behavior. Configured in `moonwell.pkl`:
`assets { paths { ... }; exclude = List(...) }`.

- Files under `assets/` import at their relative path with Windows separators. `paths` maps a
  source path to an exact in-map path. `exclude` takes exact files or directory prefixes
  ending in `/`.
- Build and test copy the imports into the staged map and merge them into `war3map.imp`.
- `assets:check` validates without writing. `assets:sync` writes the imports into the source
  map (`maps/<folder>`) for World Editor use, with:
  - hash-based ownership in `.asset-state/`;
  - case-insensitive collision checks;
  - refusal to overwrite unowned files;
  - stale removal;
  - rollback on I/O failure.

### 6.3 Map settings

Ported from wc3-dev-framework with the same behavior. The schema is `@moonwell/MapSettings.pkl`,
configured as `settings { ... }`:

- `info` and `loadingScreen` patch `war3map.w3i` (versions 18, 25, 28, 31, 32, 33, 39). They
  preserve unrelated fields and existing `TRIGSTR` references. Null inherits and `""` clears.
  Version 18 cannot set a custom loading-screen model.
- `gameplayConstants` and `gameInterface` merge section/key raw strings into
  `war3mapMisc.txt` and `war3mapSkin.txt`, preserving unspecified entries and comments.
- `gameplay` offers typed conveniences (`heroMaxLevel`, `foodLimit`). A conflicting raw value
  is an error.
- `players`, `forces` and `environment` (fog, water colour, sound environment) patch `w3i` and
  make the coordinated edits to the `config()` function in `war3map.lua` (w3i version 28+).
  Settings edits happen before bundle injection (§5 step 7 precedes step 8).

The template's `settings` block follows §3.3: every setting is written out with its default value. A setting stays
commented out only when it has a prerequisite in the World Editor, and its comment names that step. For example, a
setting that needs the map to use custom forces says so.

## 7. Packaging (MPQ writer)

`cli/src/mpq/` writes MPQ format version 1 archives:

- **Hashing.** The standard crypt table and hash functions (table offset, name A/B, file key).
  Hash and block tables are encrypted with the `(hash table)` / `(block table)` keys. The hash
  table size is the next power of two ≥ 1.5 × the file count (minimum 16).
- **Files.**
  - Files are split into 4096-byte sectors with a sector offset table. Each sector is
    deflated with `CompressionStream("deflate")` (zlib, compression byte `0x02`) and stored
    uncompressed when that isn't smaller.
  - File data is not encrypted.
  - A `(listfile)` is included. `(attributes)` is omitted.
  - Archive paths use backslashes.
- **Header.**
  - For w3i version 39 with a game build ≥ 1.31, the archive has no HM3W header.
  - Otherwise, a 512-byte `HM3W` header is prepended with the map name, flags and max players
    from `w3i`.
- **Imports.** The staged `war3map.imp` is written verbatim. Internal map files are never
  registered as imports.

## 8. Error handling

- **Errors.** All expected failures throw `MoonwellError { message, file?, line?, hint? }`,
  printed as `error: <file>[:<line>] › <message>` followed by `hint: ...`. Any other exception
  is an internal error: stack trace plus "please report".
- **Exit codes and logs.** Exit code 1 on failure. Logs go to stderr and are appended to
  `dist/moonwell.log`.
- **Tool preconditions:**
  - `pkl` missing or older than 0.32 → install link.
  - Compiler download or checksum failure → retry hint and a mention of `yue.path`.
  - Game executable missing when running `test` → names the `launch.gameExecutable` field and
    `moonwell.local.pkl`.
- **Pkl errors.** Evaluation errors pass through verbatim, since Pkl already reports file and
  line.

## 9. Testing

Repo tasks. Everything must pass on Windows and Linux unless noted.

- **`test` (unit; needs neither Pkl nor yue):**
  - Lua lexer, including strings and comments containing `require`.
  - Require graph: literal forms, dynamic require, missing module, cycles, reachability.
  - Bundle emission and line-table computation.
  - MPQ writer:
    - known-answer tests for hash functions;
    - round trips through a test-only MPQ reader in `cli/tests/support/`;
    - the HM3W header versus the headerless path.
  - Mod-file reader and writer:
    - round trips over fixtures copied from real maps (1.26-era and 1.36-era);
    - per-level lists;
    - skin splits;
    - preservation of existing objects.
  - Object validation: every rule in §6.1.
  - `w3i` patching for each supported version (fixtures), Misc/Skin txt merging, and
    `config()` edits.
  - Asset planning, ownership, collisions, stale removal, rollback.
  - Project JSON → `Project` parsing and version-mismatch detection.
  - Zip extraction, cache layout and checksum rejection (with a fake archive).
  - `gen` freshness: embedded modules match their sources.
- **`test:runtime` (needs yue):** runs the runtime Lua under `yue -e`. Covers hook ordering,
  hook error isolation, the require shim, and `format_error` line mapping, against a
  synthetic `war3map.lua` with fake `main`/`config`.
- **`test:pkl` (needs Pkl):**
  - `pkl test` over the package's schemas: valid and invalid manifests, merge duplicate
    detection, and field constraints;
  - `assets:check`/`assets:sync` and `settings:check` against a temp copy of `template/`,
    using a local package dependency.
- **`test:e2e` (needs Pkl and yue):**
  1. `init` into a temp dir.
  2. Rewrite `deno.json` and `PklProject` to the local `cli/` and `schema/`.
  3. `build`.
  4. Read the archive with the test reader and assert that:
     - `war3map.lua` contains the runtime and the entry module;
     - the object tables contain the sample object;
     - `objects.yue` matches.
- **Manual release gate** (in `CONTRIBUTING.md`):
  - Play `template/` in Warcraft III through `test` and as a packed minified `build`.
  - Confirm the startup output and the sample unit.
  - Trigger a deliberate error and confirm it prints the `.yue` path and line.
  - Open the packed map in World Editor.
  - Exercise one custom object of each category.

## 10. Release

- **Versioning.** `cli/deno.json` version, `schema/PklProject` `package.version`, and the
  embedded template's pins always share one version number.
- **Pkl package:**
  - `pkl project package pkl/` produces the zip and metadata.
  - `deno task release` creates a GitHub release tagged `moonwell@<ver>` in
    `mdlsvensson/moonwell` with both assets attached.
  - The package URI is `package://pkg.pkl-lang.org/github.com/mdlsvensson/moonwell/moonwell@<ver>`.
- **CLI:** `deno publish` from `cli/`. Tests, runtime sources and `data/` are excluded;
  `src/embedded/` is included.
- **Local development:**
  - `template/PklProject` depends on `schema/` locally: `import("../schema/PklProject")`.
  - `template/deno.json` runs `../cli/src/main.ts`.

  Developing Moonwell never requires a publish.
- **Credits.** The template's source map and the MIT attribution carried over from
  wc3-ts-template / wc3-dev-framework are kept in `LICENSE` and the README credits.

## 11. Risks and open verification (resolved in the implementation plan's first tasks)

- **Mod-file format v3 and skin flags.** The exact v3 layout (object sets) and which metadata
  column identifies skin fields must be confirmed against fixtures saved by a current World
  Editor, before the writer is built. If the SLKs do not carry a skin flag, `gen:metadata`
  gains a small, committed override list.
- **Traceback format.** The exact chunk name WC3 reports for `war3map.lua` is confirmed during
  the manual gate. `format_error` handles both forms in §5.4.
- **HM3W header correctness** for pre-1.31 maps needs one in-game check with an older-format
  map.
- **JSR scope availability** (§3.2 fallback).

## 12. Out of scope (this spec)

- Editor declarations, gameplay lint rules and Yue macros (sub-project 3).
- Libraries, typed native wrappers, and the wc3-lib port (sub-project 4).
- Hot reload.
- Reading packed `.w3x` archives as build input. Source maps are folders.
- Doodad and destructable (`w3d`/`w3b`) authoring. Those files are preserved as-is.
- macOS compiler provisioning (use `yue.path`), and Wine launch support.
