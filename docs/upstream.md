# Upstream workarounds

What Moonwell does because War3Net or CSharp.lua (War3Net.CSharpLua 2.0.4) behaves in a way it has to work around.
Each entry says what upstream does, where Moonwell handles it, the upstream issue if there is one, and what removing
the workaround would take. The evidence for each is in the workspace's `docs/game-facts.md`.

When a workaround is added or removed, update this list in the same commit.

## CSharp.lua

| # | What CSharp.lua does | Moonwell's workaround | Upstream | Remove when |
|---|---|---|---|---|
| C1 | Collection expressions (`[1, 2]`) compile to nothing in a return or field, and stop with "Compiler has a bug" in a local, assignment or argument. | Analyzer rule `CollectionExpression` (`src/Moonwell.Analyzers/Rules.cs`): a compile error with an initializer to use instead. | [Drake53/CSharp.lua#11](https://github.com/Drake53/CSharp.lua/issues/11), open | #11 is fixed in a War3Net.CSharpLua release Moonwell uses. |
| C2 | A template property used through `using static` stops the compiler (NullReferenceException in `LuaRenderer.Render`). With `using static Moonwell.Natives`, `Player.Get(0)` also fails (CS0119). | Analyzer rule `StaticNatives` (`Rules.cs`): a compile error; write `Natives.X`. | [Drake53/CSharp.lua#11](https://github.com/Drake53/CSharp.lua/issues/11), open (the crash only; CS0119 is C# name lookup) | #11 is fixed; the CS0119 part stays. |
| C3 | A C# exception carries no location: `StackTrace` is empty. | Error lines (decisions 14, 26): the build marks each statement in a copy of the project (`src/Moonwell.Build/LineMarks.cs`, `MarkedProject.cs`), and the runtime looks the Lua line up (`src/Moonwell/Core/Errors.cs`). | none | CSharp.lua writes source maps. |
| C4 | String escapes are copied into Lua as written, and Lua 5.3 refuses or reads some of them otherwise (`\e`, `\U`, short `\x`, `\0` before a digit). Raw and `u8` strings fail. | `src/Moonwell.Build/LiteralCheck.cs`: a build error with the C# line (decision 27). | none | CSharp.lua rewrites escapes for Lua. |
| C5 | `long` is 32-bit, `uint` arithmetic becomes a float, and `double` is a 32-bit float in the game. | Analyzer rule `NumberType` (MW0005): `long`, `ulong`, `uint` and `double` are compile errors in map code (decision 13). | none (the game's 32-bit Lua) | Never: the limit is the game's. |
| C6 | A class marked `@CSharpLua.Ignore` is still named as a type by generic collections, so handle types must exist in Lua. | The generated `src/Moonwell.Natives/Generated/types.lua` defines every handle type with `System.define`. | none | CSharp.lua defines ignored types itself. |
| C7 | A project and its project references compile as one assembly, so overriding a `protected internal` member needs `protected internal override`, which `dotnet build` refuses. | Lifecycle hooks are `protected`, called through `internal` methods (`src/Moonwell/Actors/*.cs`). | none | Never needed again; the design stands on its own. |
| C8 | A `ProjectReference` is compiled from source even as an analyzer (`OutputItemType="Analyzer"`), and fails on the analyzer. | `Moonwell.Analyzers.dll` is packed into the Moonwell package under `analyzers/dotnet/cs`, not referenced (`src/Moonwell/Moonwell.csproj`); fixtures reference it from a `Directory.Build.targets`. | none | CSharp.lua skips analyzer references. |
| C9 | It reads packages only from `~/.nuget/packages` (not `NUGET_PACKAGES`), never restores, needs `packageExcl` `"*"` (with `""` it decompiles the library and throws on .NET 10), and compiles a package's source, not its library. | The packages carry their C# source in `contentFiles` (`Moonwell.csproj`); `src/Moonwell.Build/PackageSources.cs` checks the source is where CSharp.lua looks and names the folder if not. | none | CSharp.lua resolves packages as NuGet does. |
| C10 | It compiles every `*.cs` under the project, `build/` included. | `src/Moonwell/buildTransitive/Moonwell.targets` removes `build/**` (in a `.targets`: a `Compile Remove` in `.props` comes before the SDK's globs and does nothing). | none | CSharp.lua honours the project's compile items. |
| C11 | `@CSharpLua.Ignore` does not skip a class's members: the generated standard objects (2.8 MB of source) cost about 10 s a build, and `Moonwell.Objects.dll` cannot be used as a library instead. | The build compiles stubs of only the used classes and members (`src/Moonwell.Build/ObjectStubs.cs`, `MOONWELL_LUA` hides the generated files) and writes their Lua itself (`ObjectLua.cs`). | none | CSharp.lua skips ignored classes cheaply, or can link a library whose base types it compiled from source. |
| C12 | Overloads are named by their order (`Set`, `Set1`, ...), and a property gets `getX`/`setX` only when it has bodies. | `ObjectStubs.cs` keeps every overload of a used name and each property's accessors; `src/Moonwell/moonwell.lua` follows the same naming. | none | Not a bug; stays while the stubs exist. |
| C13 | A member used only in `nameof` is not referenced by the assembly, so the stubs leave it out and CSharp.lua reports it missing. | `src/Moonwell.Build/LuaCompiler.cs` adds a hint to that error. | none | The stubs read names from the source as well. |
| C14 | A summary doc comment above a `@CSharpLua.Template` line makes CSharp.lua ignore the template. | Template members keep their summary below the template line (`src/Moonwell/Core/Errors.cs`, `src/Moonwell/Reactions/Hooks.cs`). | none | CSharp.lua reads the template wherever it is. |
| C15 | Its own translation errors pass `dotnet build` and come back through War3Net as `CompilationErrorException` with no `EmitResult`. | `LuaCompiler.cs` catches it and reports it as a build error with the project's paths. | none | Not a bug to remove; keep the catch. |
| C16 | An interface method with a default body is copied onto each implementing class while the script loads (`setInterface` in `Core.lua`). Before C17's fix that ran `Unit`'s static setup too early and the script stopped loading; now the copy only makes every default look written by the class, so `Hooks.Overrides` would count it. | The default methods of `IDamageSource`, `IDamageTarget` and `IDamageWatch` are marked `@CSharpLua.Ignore`, with their description as a line comment above the tag (as C14), so the Lua interface is empty (`src/Moonwell.Damage/IDamage*.cs`); the package then calls only the methods a class writes, found once per class with `Hooks.Overrides` (`src/Moonwell.Damage/Engine/Reactions.cs`), as .NET's reflection finds them. Without the tag the Lua cases load and pass (checked 10-20), but every empty default would be called on every hit. | none | CSharp.lua leaves defaults off the class, or the package tells a copied default from a written method in Lua. |
| C17 | A `Dictionary<Unit, T>` in a static field asks `Unit` for `GetHashCode` while imports are being filled, which runs `Unit`'s static setup too early: the map stops at load. | No public class of `Moonwell` or `Moonwell.Damage` has a static initializer, so there is no setup to run early: the hook tables of `Unit`, `UnitComponent`, `Item`, `ItemComponent`, `Destructable`, `DestructableComponent`, `Ability` and `MapComponent`, and `Player`'s slots, are made on first use (`src/Moonwell/Actors/*.cs`, `src/Moonwell/Abilities/Ability.cs`). `tests/Moonwell.Tests/StaticSetupTests.cs` keeps it so, and the Lua case `units.dictionary-key` loads a static `Dictionary<Unit, string>` from a file that sorts before `Unit.cs` (`tests/Moonwell.Testing/KeyedNames.cs`). A map's own class with a static initializer is still not a safe key: the guide says to key by the handle. | none | As C16; then the hook tables can be static fields again. |
| C18 | A whole-number `float` literal is emitted as a Lua integer, so such floats do integer arithmetic and wrap past 2^31; a constant it folds or inlines (`16777216f + 1f`, a const, a cast, an int stored in a float, a left-out default argument) is written by its value, also without a point; a conversion from an int to a float is dropped (`(float)count` is `count`), and a float field starts at `0`. | Map code: `src/Moonwell.Build/FloatLiterals.cs` rewrites the marked copy, each whole-number `float` or `double` constant as the one literal of its value with a point (`16777216.0f`), which CSharp.lua copies as written, and a left-out whole-number default into the call, named; `RunTimeFloats.cs` adds `+ 0.0f` to an int made a float at run time (`((float)count + 0.0f)`, `(count * 1000000 + 0.0f)`: the int is still worked out first, as in C#) where Lua would keep the integer (not beside a float in `+ - * %`, nor in `/`, a comparison or `x += n`, unless the operator is user-defined), also an int passed to a user-defined conversion taking a float, and `= 0.0f` to a float or double field or auto-property without an initializer; a name it cannot resolve fails the build. Moonwell's own source, compiled from its packages, is written with points, `+ 0.0f` and initializers (a const used in code is a field instead, as `NativeWorld`'s lap), the generator writes whole `real` constants as `270.0f`, and `tests/Moonwell.Build.Tests/PackageFloatsTests.cs` fails on anything the rewrite would change. Object data floats get a point too (`FieldValues.cs`). Not covered: an `int?` made a `float?` (`float? f = maybe;`, null stays null), `foreach (float f in ints)`, a struct's own float field, a float array's items (`new float[n]` holds integer `0`s), `Math.Floor` and `Math.Ceiling` (Lua's `math.floor` and `math.ceil` give integers), and a base constructor's whole default is not written in when no `: base(...)` is written (a constructor that leaves the call out, or a class with no constructor); one reached through `: base(...)`, `: this(...)` or a primary constructor's base is. A whole float prints as `50.0` where C# prints `50`. | none | CSharp.lua writes float literals and folded float constants with a point, keeps a conversion from an int to a float, and starts a float field at `0.0`. |
| C19 | A project reference is compiled from source with everything it references (as C8), so a library referencing `Moonwell.Objects` brings every generated standard class into the Lua of whatever compiles it, and their getters need the objects library the build appends (`MoonwellObjects`). | `src/Moonwell.Damage/Moonwell.Damage.csproj` references `Moonwell`, not `Moonwell.Objects`, so the Lua cases (`tests/Moonwell.Testing`) can run the package. | none | C11's cost is gone and the Lua cases carry the objects library; then the package can use `Moonwell.Objects` directly. `AttackType` and `DefenseType` are core enums since 0.2.1 (`src/Moonwell/Types`), so the package needs neither of them from it. |

## War3Net

| # | What War3Net does | Moonwell's workaround | Upstream | Remove when |
|---|---|---|---|---|
| W1 | 6.1.1's bundled `TriggerData.txt` lists `UnitOrderChallengingCall` twice, so `Map.Open` and `new MapScriptBuilder()` throw on any map. The parser still throws on a duplicate in a supplied copy. | `src/Moonwell.Build/SourceMap.cs` opens the map without its GUI trigger files, and `LuaCompiler.cs` passes `triggerData: null`. | [Drake53/War3Net#105](https://github.com/Drake53/War3Net/issues/105), closed; fixed in 6.1.2 (PR #106) | Kept on purpose: Moonwell has no GUI triggers to read. |
| W2 | Without `war3map.w3e` it writes `config` but no `main`, and the game crashes before the load screen. | `LuaCompiler.cs` fails the build when the script has no `main`. | none | War3Net writes `main` or refuses the map. |
| W3 | `War3Net.IO.Slk` 6.0.2 types each cell: decimals become `float`, `#VALUE!` and `#REF!` become 0, and an unquoted cell it does not know throws. | Moonwell reads SLK files with its own reader (`generator/Moonwell.Generator/Objects/ExportTables.cs`); see the evaluation in the workspace notes. | [Drake53/War3Net#108](https://github.com/Drake53/War3Net/issues/108), open | A release has a keep-text mode; switching then gives the same output. |
| W4 | Names the Forsaken Kingdom game data version `Unset` (value 2). | `src/Moonwell.Build/GameData.cs` maps Forsaken Kingdom to `GameDataVersion.Unset`. | none | War3Net names the value. |
